# 1:1 원격 제어 (PR #109)
윈도우 내장 Desktop Sharing(WDS)을 쓴다. 화면 전송 · 입력 주입 · 커서를 전부 OS 가 하므로
우리 코드가 하는 일은 네 가지뿐이다 — 입력 잠금 해제 · 방화벽 인바운드 개방 ·
공유 세션을 열어 접속 문자열 전달 · 붙은 교수에게 조작 권한 부여.
자리는 화면 모니터링 상세보기의 [🖥 원격 제어], 1:1 고정(동시 1개).

- 패킷 72~75(Start · Invitation · Stop · Failed). 네이티브는 중계만 하므로 **DLL 재빌드 불필요**
- 연결 방향은 **학생이 리스너, 교수가 접속해 온다** → 교수 PC 는 포트도 관리자 권한도 필요 없다.
  학생 쪽은 공유 세션이 NIC 마다 매번 다른 포트를 열기 때문에 포트 규칙을 쓸 수 없고,
  **프로그램 경로 기준 인바운드 규칙**을 켤 때 넣고 끝날 때 지운다
- **`CTRL_LEVEL_INTERACTIVE` 는 3 이다** (Windows SDK `um\rdpencomapi.idl`: 1=NONE, 2=VIEW, 3=INTERACTIVE).
  2 를 넣어 '보기 전용'이 됐고, 게다가 참석자가 2 로 붙기 때문에 "이미 줬다"로 건너뛰어
  **화면만 가고 입력이 안 갔다.** 값을 3으로 고치고 올린 값을 되읽어 확인하게 한 뒤 실기에서 조작 확인
- 통제 · 시험 상태로 바꾸면 원격을 먼저 끊는다(잠금과 덮개가 교수 입력까지 막기 때문)
- **한/영 · 한자 키는 화면 공유로 전달되지 않는다 — 패킷 76 으로 따로 보낸다.**
  `VK_HANGUL`(0x15)은 `VK_KANA` · `VK_JUNJA` 와 같은 **IME 키 묶음**이라 IMM32 가 누른 PC 에서 먹어 버리고,
  전용 키의 스캔코드(한/영 `0xF2` · 한자 `0xF1`)도 RDP 가 나르는 표준 범위 밖이며 뗌이 없는 키다.
  그래서 교수 창이 저수준 훅으로 IMM 보다 먼저 가로채 **키를 삼키고**(안 삼키면 교수 PC 의 한글 상태만
  몰래 바뀐다) 패킷으로 보내고, 학생 앱이 자기 PC 에 `SendInput` 으로 눌러 준다.
  훅은 **이 창이 맨 앞일 때만** 가로챈다 — 아니면 교수 앱의 다른 입력칸에서 한글을 못 쓴다.
  참고로 **오른쪽 Alt** 는 평범한 스캔코드(`E0 38`)라 패킷 없이도 전달되고, 학생 PC 가 101키 호환
  (`OverrideKeyboardIdentifier = PCAT_101A/B/CKEY`)으로 설정돼 있으면 그 PC 가 한/영으로 해석한다.
  103/106키로 설정된 PC 에서는 Alt 가 안 먹으므로 패킷 경로가 유일한 방법이다
- 실기 때 쓸 확인 목록은 기억 `next-remote-control` 에 있다

## 2. 시험 시작 직후 학생 앱이 꺼지고, 압축이 풀리지 않는다 — 원인 찾아 고쳤다(2026-10-28)
**증상이었던 것**: 시험 시작 뒤 시험 모드로 바꾸면 학생 앱이 종료되고 연결이 끊겼다.
시험 파일은 받아졌으나 압축 해제가 되지 않았다.

### 원인 — `ShowActivated=false` 인 창을 최대화한 채로 보이게 했다
```
System.InvalidOperationException:
  ShowActivated가 false이고 WindowState가 Maximized로 설정되어 있으면 창을 표시할 수 없습니다.
   at StudentExamWindow.PresentExamWorking()   ← Visibility = Visible
   at StudentExamWindow.UpdatePresentation()
   at StudentExamWindow.OnClassModeChanged()
   at ClassControlService.ApplyModeCore()      ← ModeChanged?.Invoke(mode)
```

`StudentExamWindow` 는 **로그인 직후 큰 창이 번쩍이지 않도록 `ShowActivated = false` 로 만들어진다**(생성자).
그런데 `PresentExamWorking()` 은 `WindowState = Maximized` 로 둔 채 `Visibility = Visible` 을 준다.
WPF 가 이 조합을 거부하고 예외를 던지는데, 화면 스레드에서 나는 예외라 그대로 앱이 죽었다.

- **`PresentExamWorking()` 만 `Maximized` 다.** 덮개(`PresentCover`)와 자유·숨김은 `Normal` 이라 멀쩡했다.
  그래서 **(시험 모드) AND (시험 시작됨)** 이 처음 참이 되는 순간에만 터졌다 — 두 순서 모두 이 한 곳으로 모인다
- 고친 것: `Maximized` 를 주기 전에 `ShowActivated = true` 로 되돌린다(한 줄).
  시험 작업 창은 어차피 앞으로 나와야 하므로 의도에도 맞는다
- **압축이 안 된 이유**: 교수는 `ProcessListUpdate` → `ExamPhaseChange` → `ExtractArchive` 를 연달아 보내는데,
  시험 모드 전환으로 먼저 죽으면 그 뒤 `ExtractArchive` 를 처리할 앱이 없다. 받은 .7z 만 남는다
- 검증: 교수 앱 없이 학생 앱만 띄워 두 순서를 모두 재현했다(고치기 전 터짐 → 고친 뒤 통과).
  **유예 15초 끝의 `ForegroundCleanup.KillUserWindows()` 는 개발 PC 의 창을 전부 닫으므로 재현에서 건드리지 말 것**

### 크래시 기록도 함께 붙였다(2026-10-27)

`StudentUI\App.xaml.cs` 의 크래시 그물은 `(_, _)` 로 받아 예외를 **버리고 있었다.**
이제 두 그물이 **바탕화면의 `crash.log`** 에 예외 종류 · 메시지 · 스택을 덧붙인다
(숨은 폴더에 두면 강의실에서 경로를 불러 주며 찾게 해야 한다 — 바탕화면이면 "바탕화면의 crash.log 보내 주세요"로 끝난다)
(`StudentUI\Service\CrashLog.cs`). 일부러 예외를 내 양쪽 그물에서 파일이 생기는 것까지 확인했다.
파일은 BOM 없는 UTF-8 이라 **PowerShell 5.1 의 `Get-Content` 로 읽으면 깨져 보인다** — `-Encoding UTF8` 을 주거나 메모장으로 열 것.

**다음 할 일**: 강의실에서 한 번 재현하고 `crash.log` 를 볼 것. 그 전까지는 추측이다.

- 왜 죽는지 가장 그럴듯한 길: 학생 앱의 패킷 처리기는 **네이티브 수신 스레드에서 그대로 돈다**
  (`NetworkService.cs:27` → `NetworkInterop.cs:1198`). 사이에 try/catch 가 한 군데도 없어,
  처리기 하나가 예외를 던지면 네이티브로 넘어가 **프로세스가 즉사**한다.
  교수가 [시험 시작]을 누르면 `ProcessListUpdate` → `ExamPhaseChange` → `ExtractArchive` 세 개가
  연달아 간다(`ExamFlowService.cs:22`). **앞의 둘에서 죽으면 압축 해제 패킷은 처리되지 못한다** —
  "파일은 받았는데 압축이 안 풀렸다"와 맞는다
- 압축 해제·감시 시작 경로는 예외를 잡게 고쳤다(`ExamFileStore.StartExamAsync`).
  화면 스레드에 맡긴 `async void` 라 예외가 하나라도 새면 앱이 죽던 자리다.
  이제 잡아서 `crash.log` 에 적고 학생 화면에 "시험 시작 처리 실패: … — 교수님께 재배포를 요청해 주세요"로 남긴다.
  늦게 도착한 파일을 풀던 `StartLateAsync` 도 같은 자리로 합쳤다(그쪽에는 잡는 자리가 아예 없었다)
- 시험 시작 직후 학생이 **동시에** 하는 일이 많다: 압축 해제 · 감시 시작(`ExamMonitorService`, :78 에서
  `ExamStartHandled` 를 듣는다) · 상태 전환(`ClassControlService`, 유예 15초 창) · 방화벽 차단
- 학생 앱이 **일부러 죽는 정책**인 것도 염두에 둘 것(상태가 깨진 채 시험을 이어 가지 않는다).
  죽는 것 자체는 설계이고, 문제는 **죽을 만한 예외가 난다는 것**이었다. 이유가 안 남던 것은 이제 해결됐다
- **아직 안 한 것**: 이 실패를 **교수에게 알리는 길**이 없다. 학생 화면에만 뜬다.
  쓸 만한 기존 패킷이 없어서(`StudentStatus.FileMissing` 은 5초 점검이 곧바로 되돌리고,
  `MonitorStatusReport` 는 문구가 '인터넷 차단 실패'로 나간다) 손대지 않았다. 새 보고 경로가 필요하다
- **4번과 겹친다**: 압축이 안 풀린 학생은 교수 기록상 '수신완료'라 재배포 대상에서 빠진다

## 3-2. 로그인이 실패해도 학생이 그냥 들어가졌다 — 막았다(2026-10-28)
**증상**: 교수 앱이 쓰던 9000 번 포트가 갑자기 막혀(다른 프로그램이 차지) 학생이 접속하지 못했는데,
**학생 앱은 아무 말 없이 자유 모드 화면까지 열렸다.** 교수 대시보드에는 그 학생이 없고 채팅도 가지 않았다.
(현장 조치는 교수 [포트 변경]으로 8000 번으로 옮겨 해결.)

**원인**: `LoginService.LoginAsync` 가 **회신이 없으면 승인으로 쳤다.**
```csharp
// 예전: 회신이 오지 않으면 승인된 것으로 보고 넘어간다
string? rejection = finished == response.Task ? response.Task.Result : null;
```
TCP 연결 자체는 **그 포트를 쓰는 아무 프로그램에나** 붙으면 성공한다. 그래서 교수 앱이 아닌 것에 붙어도
`Connect` 는 true 였고, 회신이 없어도 3초 뒤 통과했다.

**고친 것**: 회신이 없으면 `NoResponse` 로 실패시킨다. 기다리는 시간은 3초 → 5초.
교수 앱은 **네이티브가 로그인 패킷을 받는 즉시** 승인이든 거절이든 반드시 회신하므로
(`ProfessorServer::HandleLogin` — 교수 화면이 바빠도 영향 없음), 회신이 없다 = 우리 교수 앱이 아니다.
학생 앱은 교수 앱 없이는 뜻이 없으니 애매하면 들여보내지 않는 쪽이 맞다.

- 학생에게 보이는 안내: 연결된 주소·포트와 함께 "교수 프로그램이 응답하지 않습니다 /
  다른 프로그램이 같은 포트를 쓰고 있을 수 있습니다" + 교수님께 확인을 청할 세 가지
  (프로그램 켜짐 · '서버 활성화' · 포트 번호, 다르면 [포트 변경])
- 자동 재연결도 같은 경로를 쓰므로 함께 막힌다(`ReconnectService`)
- 검증: 받기만 하고 아무 말 없는 서버 → `NO_RESPONSE` 로 막힘, 진짜 교수 앱 → 그대로 승인. 둘 다 실행으로 확인
- **교수 쪽은 손대지 않았다** — 상단바에 "서버 꺼짐 (서버를 열지 못함)" 표시와 [서버 다시 열기] · [포트 변경]이 이미 있다

## 4. 시험 시작 뒤 앱을 다시 켜면 파일을 다시 보낼 길이 없다

- 필요한 것은 둘 중 하나(또는 둘 다):

  **(b)** 시험 중에도 준비 단계를 다시 열 수 있게 하는 길.
  어느 쪽이든 **덮어쓰기 위험을 교수가 알고 누르게** 만들어야 한다

  패킷을 보내지 않는다. 실제 삭제는 **학생이 답안을 낼 때 스스로** 한다(`AnswerSubmitService.CleanupExamFiles`).
  2026-09-22 에 교수님 지시로 셧다운을 들어내면서 기록만 남게 된 것이다
- N 도 틀렸다 — `CollectedCount`(수집 완료 전원)라 "2명 지운다"처럼 보이는데 체크를 안 하면 0명이 처리됐다.
  지금은 **체크된 처리 가능 학생 수**이고, 0명이면 버튼이 비활성이다
- **그래도 없애지 않은 이유**: 이 기록이 왼쪽 메뉴 배지(`ApprovalWaitingCount`)와
  [처음 화면으로] 잠금의 근거다. 특히 '흔적 삭제'가 **오류**인 학생을 못 보고 다음 시험으로 넘어가는 것을
  막는 유일한 장치다

## 나. 학생 시험 화면을 덮개로 통일하고, 정리가 끝나면 스스로 닫는다
시험이 **도는 동안에만** 큰 창을 숨기고, 앞뒤는 덮개다.

| 상태 | 화면 |
|---|---|
| 시험 모드 · 시작 전 | 전체화면 덮개(대기) |
| 시험 모드 · **진행 중** | **숨김 + 남은 시간 · 제출 PIP 만** |
| 시험 모드 · 끝난 뒤 | 전체화면 덮개(종료 잠금 화면) |

- 예전에는 시작하는 순간 덮개가 전체 작업 창으로 바뀌어 **바탕화면을 가린 채 PIP 와 둘 다** 떠 있었다
- 쓰이지 않게 된 `PresentExamWorking` 을 지웠다. 거기 적혀 있던 `ShowActivated=false` + `Maximized` 함정은
  값을 설정하는 생성자로 옮겼다 — 지금은 보이는 모습이 전부 `WindowState.Normal` 이라 걸릴 일이 없다
- **제출 → 교수 수신 확인 → 흔적 삭제** 가 끝나면 덮개에 초록 상자로 알리고 **5초 뒤 앱을 닫는다.**
  닫히면 `App.OnExit` 가 키보드 잠금과 인터넷 차단을 풀어 그 PC 가 자유로워진다
- **정리에 실패하면 닫지 않는다.** 시험 파일이 남아 있는데 덮개를 걷으면 다음 사람이 앞사람 답안을 본다.
  그때는 "교수님께 알려 주세요"가 남고 교수 표의 '흔적 삭제'가 **오류**가 된다
- 신호는 `AnswerSubmitService.CleanupFinished(bool)` 로 새로 뺐다 — `StateChanged` 로는 가를 수 없다.
  **정리에 실패해도 제출 자체는 `Succeeded`** 이기 때문이다

## 마. 로그인 직후 검은 창이 번쩍였다 (PR #119)
**증상**: 로그인하고 자유 모드 PIP 가 뜨기 전에, 제목 표시줄만 있는 **검은 창이 0.2초쯤** 떴다 사라졌다.

**원인**: `App.OnCurrentViewModelChanged` 가 `nextWindow.Show()` 를 **무조건** 불렀다.
`Show()` 는 실제 Win32 창을 만들어 화면에 올린다. 그 뒤 `Loaded` → `PresentFree()` 에서 숨겨도 이미 늦어,
**내용을 그리기 전의 빈 창**이 그대로 보인다.

- 생성자의 `WindowState = Minimized` 로 가려 보려 했지만 **오히려 길을 하나 더 열었다.**
  숨긴 직후 `WindowState = Normal` 을 주면 윈도우가 `ShowWindow(SW_RESTORE)` 를 부르는데,
  이 함수는 복원하면서 **창을 다시 보이게 한다.** WPF 의 `Visibility` 속성은 `Hidden` 인데 실제 창은 떠 있는 상태가 된다
- **WPF 의 `Visibility` 로는 검사할 수 없다** — 실제로 한 번 속아 "고쳤다"고 보고했다가 되돌렸다.
  창이 진짜 보이는지는 `IsWindowVisible` 로 봐야 한다

**고친 것**: 숨길 창은 **아예 만들지 않는다.**

- `App` 은 시험 창에만 `Show()` 대신 `StudentExamWindow.Present()` 를 부른다.
  `Present()` 가 지금 상태를 보고 정하고, 자유 · 통제 · 시험 중이면 창을 만들지 않는다
- 덮개가 필요해지면 `PresentCover()` 의 `Visibility = Visible` 이 그때 띄운다 —
  **WPF 에서 `Visibility` 를 `Visible` 로 주는 것은 `Show()` 를 부르는 것과 같다.**
  `PresentCover` 는 `ApplyFullScreenBounds()` 를 보이기 전후로 두 번 부르므로 핸들이 없던 첫 호출도 처리된다
- 생성자의 `Minimized` 와 숨김 경로의 `WindowState` 조작을 **둘 다 없앴다.**
  숨긴 창에 `WindowState` 를 건드리는 것이 창을 되살리던 바로 그 길이다
- `Loaded` 로 화면을 잡던 것을 `Present()` 로 옮겼다 — `Loaded` 는 `Show()` **뒤에야** 오므로
  "띄우지 않기"를 거기서 결정할 수 없다
- 검증: 배경 스레드에서 5ms 마다 `IsWindowVisible` 로 실제 창을 찍어 양방향 확인했다.
  자유 = PIP(688×482)만 뜸, 덮개 전환 = 큰 창이 전체화면(2910×1830)으로 뜸.
  덮개 쪽은 모드 전환 대신 `PresentCover` 를 직접 불렀다 — 모드 전환에는 유예 15초와
  `ForegroundCleanup.KillUserWindows()` 가 딸려 와 개발 PC 의 창을 전부 닫는다

## 7. 답안 제출 경로를 전면 손질했다 (PR #127) — 이 묶음에서 가장 큰 변경
사용자 지시: *"다른 쪽 버그는 괜찮으나 이 쪽 버그는 무슨 일이 있어도 막아야 한다."*
30~40명이 동시에 답안을 내는 상황에서 **전송 실패 · 파일 손상 · 이름 깨짐**이 나면 시험 자체가 무의미해진다.
스레드 동작을 전수로 훑어 **실제로 존재하는 결함 6개**를 찾아 고쳤다.

| | 결함 | 고친 방법 |
|---|---|---|
| ① | 저장이 15초를 넘으면 **멀쩡한 학생이 하트비트 만료로 끊겼다** — 교수 PC 에는 답안이 있는데 학생은 '제출 실패'를 본다 | `ClientSession::busy` 를 두고 감시가 건너뛴다. 켜고 끄는 일은 `SaveGuard`(RAII)에 맡겨 예외로 빠져나가도 반드시 풀린다 |
| ② | 보내기 타임아웃 뒤에도 **같은 연결을 계속 썼다** — 이미 일부 바이트가 나간 뒤라 패킷 경계가 어긋나 이후 전송이 전부 실패 | 실패하면 그 연결을 버린다. 자동 재연결이 깨끗한 새 연결을 만든다 |
| ③ | 저장에 성공하든 실패하든 **임시 파일을 지웠다** | 성공했을 때만 지운다. 실패하면 증거로 남긴다 |
| ④ | `StudentStore.Students` 를 **배경 스레드에서 잠금 없이 훑었다** | 변경·조회를 `Gate` 로 잠그고 `TryResolveBySession` 추가 |
| ⑤ | 조각을 받아 쓰는 동안 **공용 잠금을 쥔 채 디스크를 만졌다** — 한 학생의 느린 쓰기가 전원을 막는다 | 수신 기록을 `shared_ptr` + 전송별 `writeMutex` 로 분리 |
| ⑥ | 전송 중 끊긴 학생의 **열린 파일 핸들과 반쯤 받은 임시 파일이 남았다** | `FileTransferReceiver::AbortBySender` 를 연결 종료 시 부른다 |

**잠금 순서는 두 경로 모두 `contextsMutex_` → `writeMutex` 로 같다.** 뒤집히는 길이 없어 교착이 성립하지 않는다.

**실측으로 확인한 것** (흉내 학생 스크립트)
- 30명 동시 제출 → **30/30 성공**, 가장 늦은 확인 회신 3.65초(고치기 전 4.26초)
- 전송 도중 8명 강제 끊김 → 교수 PC `%TEMP%` 에 남은 `NL_*` **0개**
- 끊김 10명 + 제출 20명 동시 → **20/20 성공**, 교수 앱 생존

**확인하지 못한 것 — 실기에서 꼭 볼 것**
- **①②는 발동 자체를 못 봤다.** 저장 15초 초과, 보내기 10초 초과를 개발 PC 에서 만들 수 없었다.
  큰 묶음(100MB 이상)으로 30명 동시 제출, 제출 도중 랜선 뽑기로 확인할 것
- 7za 가 멈추면(`WaitForSingleObject(..., INFINITE)`) `busy` 가 켜진 채 남아 **그 세션은 하트비트로도 안 닫힌다.**
  고치기 전에도 그 수신 스레드는 멈춰 있었으니 거래를 한 셈이다
- ②는 **한 바이트도 못 보낸 실패(파일 열기 실패 등)에서도 연결을 끊는다.** 일부러 안전한 쪽으로 기울였고,
  대신 학생이 보는 문구가 원인과 무관하게 '전송이 끊겼습니다'로 뭉개진다
- `ClientSession` 의 **종료 시점 use-after-free 는 그대로 남아 있다.** 수신 스레드를 `detach()` 하는데
  소멸자는 `joinable()` 이 false 라 거두지 못한다. 고치려면 `enable_shared_from_this` 로 수신 스레드가
  자기 세션의 참조를 들게 해야 한다(약 6줄). **`detach()` 를 그냥 걷어내면 안 된다** —
  학생이 정상 종료할 때 소멸자가 수신 스레드 자기 위에서 돌아 **자기 자신을 join** 하다 즉사한다

- **`ClassModeState`** — 학생 PC 상태(자유 · 통제 · 시험)를 교수 앱이 기억하고 **접속할 때마다 다시 보낸다.**
  학생 앱은 끊기는 순간 잠금을 스스로 푸는데(그 자체는 맞다), 다시 붙을 때 아무도 알려 주지 않아
  랜선이 한 번 흔들린 학생만 혼자 자유 상태로 남았다. 전체 전환과 개별 전환을 함께 담는다
- **화면 캡처를 배경 스레드로** — 한 장에 썸네일 56ms · 고화질 68ms(실측)가 화면 스레드에서 돌았다.
  시험 중에는 저수준 키보드 훅이 같은 스레드에 걸려 있어 키 입력이 밀리고,
  윈도우의 훅 응답 한계(기본 300ms)를 넘기면 **운영체제가 훅을 조용히 떼어 버린다**(탈출키 차단이 말없이 풀린다).
  앞 장이 안 끝났으면 이번 차례는 건너뛴다 — 밀어 두면 느린 PC 에서 캡처가 쌓인다

## 8. 수동 IP 로그인에서 학생 앱이 '응답 없음' 이 됐다 (PR #128)
**증상**: 자동 탐색이 실패해 주소를 직접 입력했는데 연결이 안 되는 경우,
"연결 실패"가 떠야 하는데 **학생 앱이 통째로 멈추고 '응답 없음'** 이 떴다.

**원인은 두 겹이다.**
1. 네이티브 `StudentClient::Connect` 가 **블로킹 `connect()`** 였다. 상대가 아무 답도 주지 않으면
   윈도우가 SYN 을 재전송하며 **약 21초**를 기다린다
2. `LoginViewModel.CompleteLogin` 이 그것을 **화면 스레드에서 동기로** 불렀다.
   `async Task` 메서드지만 첫 `await` 가 아홉 줄 뒤라 `Connect` 는 화면 스레드에서 끝까지 돈다

> 존재하는 PC 인데 포트만 닫혀 있으면 RST 가 즉시 와서 정상적으로 실패한다.
> **없는 주소를 쳤을 때만** 멈추는데, 그게 바로 오타 상황이다.

**고친 것 — 둘 다 해야 한다**
- 네이티브: 소켓을 잠깐 논블로킹으로 바꿔 `connect` 를 걸고 `select` 로 **3초**(`CONNECT_TIMEOUT_MS`)만 기다린 뒤
  **다시 블로킹으로 되돌린다.** 되돌리는 것이 중요하다 — 받기 루프와 `SO_SNDTIMEO` 가 블로킹 소켓을 전제로 돈다.
  `select` 가 깨어난 것만으로는 성공이 아니라서 `getsockopt(SO_ERROR)` 로 한 번 더 본다(**거절당해도 깨어난다**)
- C#: `await Task.Run(...)` 으로 배경 스레드에 넘기고 "연결하는 중…"을 띄운다
- 1번만 하면 3초 굳고, 2번만 하면 21초 동안 "연결하는 중…"이 떠 있다
- **덤으로 고쳐진 것**: `ReconnectService` 도 같은 호출을 쓴다. 배경 스레드라 화면은 안 멈췄지만
  **한 번 시도에 21초**가 걸려 3초 재시도 간격이 무의미했다

## 9. 통제 모드 버튼이 눌렸는지 알 수 없었다 (PR #129)
구별 수단이 **글자 굵기뿐**이었다(`FontWeight` Bold/Normal 세 줄). 셋 다 같은 검은색으로 채워져 있어
상단바의 작은 버튼에서는 차이가 보이지 않았다.

- **켜진 것만 채우고 나머지는 테두리만** 둔다(`ClassModeButton` 스타일, `Tag="on"` 트리거).
  흰 상단바 위에서 채움과 테두리는 멀리서도 갈린다
- 파랑(`BtnPrimary`)은 쓰지 않았다 — '지금 해야 할 일' 하나에 쓰는 색이고, 모드 표시는 **동작이 아니라 상태**다.
  (파랑 안도 그려서 비교했고 사용자가 검정 채움으로 정했다)
- **`MainWindow.xaml` 에 박혀 있던 `FontWeight="Bold"` 를 지워야 한다** —
  WPF 는 로컬 값이 스타일 트리거보다 우선하므로, 두면 꺼진 버튼도 계속 굵다
- `MinWidth` 로 폭을 고정했다. 켜진 버튼만 굵어지면 폭이 달라져 **버튼 줄이 좌우로 흔들린다**
- 상세보기(`DetailMonitoring`)에도 같은 방식을 넣되 **명암을 뒤집었다** — 바탕이 `#1A1D21` 이라

## 10. 시험 진입 유예와 테스트 탈출키 (PR #130)
- **유예 15초 → 5초.** 이 시간은 교수가 [시험 시작]을 누른 뒤 학생 화면이 바뀔 때까지의 기다림이기도 해서,
  길면 교수가 안 걸린 줄 알고 다시 누른다. 그만큼 **학생이 저장할 시간은 짧아지므로**,

- 잠긴 채 갇힐 걱정은 받쳐져 있다 — 교수 PC 와 끊기면 학생 앱이 스스로 전부 푼다(`Disconnected → ReleaseAll`)

# 강의실 배포판 (2026-11-02 에 형식을 바꿨다)

**`교수용1102` · `학생용1102`** 가 기준이다. 그 전 형식(`교수용1029` 등)은 **닷넷이 없는 PC 에서 돌지 않는다.**

## 왜 바꿨나 — 옛 형식은 런타임을 넣은 척만 하고 있었다
`교수용1029` 같은 폴더는 `runtime\host` · `runtime\shared` 에 닷넷 런타임을 통째로 담고 있었지만,
**그 폴더는 한 번도 쓰인 적이 없다.**

- `runtimeconfig.json` 에 `"frameworks"` 가 있으면 **설치된 닷넷을 찾는** 빌드다
- 그 `.exe` 는 **180KB 짜리 껍데기**이고, `DOTNET_ROOT` 환경변수나 `C:\Program Files\dotnet` 만 본다
- **`runtime\` 이라는 이름은 닷넷 규약에 없다.** 개발 PC 에서 잘 돌던 것은 거기 닷넷이 깔려 있어서다

## 지금 형식 — 자립형 단일 파일
```
dotnet publish <앱>.csproj -c Release -r win-x64 --self-contained true \
  -p:SolutionDir="C:\Bash\exam-management-system\ExamManager\" \
  -p:SatelliteResourceLanguages=en \
  -p:PublishSingleFile=true -p:IncludeNativeLibrariesForSelfExtract=false \
  -p:EnableCompressionInSingleFile=true
```

| | 파일 | 폴더 | 크기 |
|---|---|---|---|
| `교수용1029` (옛 형식) | 494개 | 22개 | 188 MB |
| `교수용1102` | **13개** | **0개** | **77 MB** |

- `SatelliteResourceLanguages=en` — 안 주면 **언어별 리소스 폴더 13개**(`cs` `de` `ja` `ko` …)가 생긴다.
  앱이 쓰는 한글은 코드에 박혀 있어 영향 없고, 영어가 되는 건 닷넷 내부 예외 메시지뿐이다
- **`IncludeNativeLibrariesForSelfExtract=true` 는 쓰면 안 된다.** 파일이 2개까지 줄지만
  **`7za.exe` 까지 exe 안으로 들어간다.** 코드는 `AppContext.BaseDirectory` 에서 `7za.exe` 를 찾는데
  단일 파일에서 그 값은 **exe 가 있는 폴더**이지 추출 폴더가 아니다 → 답안 압축 · 해제가 통째로 실패한다
- WPF 네이티브(`wpfgfx_cor3` 등)도 같은 이유로 파일로 둔다. 강의실 PC 는 로그인마다 `%TEMP%` 가
  초기화되는 경우가 많아, exe 에 넣으면 매번 수십 MB 를 풀어내며 첫 실행이 느려진다

## 반드시 함께 넣어야 하는 것
- **MSVC 런타임 3개** — `vcruntime140.dll` · `vcruntime140_1.dll` · `msvcp140.dll`.
  우리 네이티브 DLL 셋이 전부 `/MD`(동적 CRT)라 이게 없으면 **`FileControl.dll` 로드부터 실패**한다.

- **`7za.exe`** — 프로세스로 실행하므로 반드시 파일이어야 한다
- **네이티브 3개를 Release 로 다시 빌드해서** 넣을 것. 옛 DLL 이 섞이면 겉보기는 똑같이 도는데

- `.pdb` 는 넣어도 되고 빼도 된다. 넣으면 바탕화면 `crash.log` 의 스택에 **파일명과 줄 번호**가 찍힌다

- **조용한 실패를 남기지 말 것** (2026-10-27 사용자 지시). `catch { Debug.WriteLine(...) }` 로 끝나는 코드와
  아무 말 없는 `return` 은 그 자체로 결함으로 본다 — 교수는 학생 PC 앞에 없고 학생은 교수 화면을 못 보기 때문에,
  한쪽의 실패를 로그로만 남기면 양쪽 모두 "눌렀는데 아무 일도 안 일어난다" 만 보게 된다.
  **끝났다는 사실도 전달 대상이다.** 상대 PC 의 실패는 패킷으로 이유를 보내서라도 보여 준다(원격 제어의 패킷 75 가 그 용도)
- **배포판 빌드** — `.sln` 이 없어 csproj 를 직접 빌드하면 `$(SolutionDir)` 가 비고 네이티브 DLL 이 **조용히 빠진다**(빌드는 성공한다).
  항상 `-p:SolutionDir="C:\Bash\exam-management-system\ExamManager\"` 를 준다.
  **vcxproj 도 똑같다** — 안 주면 네이티브가 `ExamManager\<프로젝트>\x64\Release\` 로 나가고,
  csproj 가 보는 `ExamManager\x64\Release\` 에는 옛 DLL 이 그대로 남는다(2026-10-27 에 겪었다).
  `x64\Release` 의 네이티브 DLL 이 Release 인지도 확인할 것(Debug CRT 는 강의실 PC 에서 로드가 실패한다).
  **강의실에 들고 갈 폴더를 만드는 절차는 위 '강의실 배포판' 절에 따로 적어 두었다** — 자립형 단일 파일,
  MSVC 런타임 3개, `7za.exe` 를 exe 안에 넣으면 안 되는 이유까지
- **단일 파일에서 깨지는 API** — `Assembly.Location` 은 **빈 문자열**이 된다. 지금 저장소에는 쓰는 곳이 한 곳도 없고
  `AppContext.BaseDirectory`(exe 폴더를 가리킨다)와 `Environment.ProcessPath` 만 쓴다. 새로 쓸 때 이 둘만 쓸 것
- **pack URI** — 두 앱이 글자 크기를 나눠 쓰게 된 뒤로 pack URI 에 어셈블리 이름을 반드시 적어야 한다
  (`pack://application:,,,/StudentUI;component/FontSizes.xaml`). 틀어지면 **빌드는 통과하는데 화면이 전부 안 열린다**
- **화면을 지우거나 이름을 바꾼 배포**는 게시 뒤에 그 화면을 **실제로 만들어 봐야** 한다.
  빌드도 통과하고 `x:Class` 와 클래스 이름이 어긋나도 그 화면을 열 때만 터진다.
  스크래치의 `packcheck` 에 `--window <전체 타입명>` 을 주면 게시 폴더에서 어셈블리를 올려 생성해 본다
  (교수 화면은 전부 `UserControl` 이라 `Window` 로 캐스팅하지 않는 판이어야 한다).
  게시된 DLL 에 타입 이름이 들어갔는지는 `grep -a <타입명> App.dll` 로도 보이지만,
  **BAML 은 압축된 `.g.resources` 안이라 grep 으로 안 보인다** — 없다고 오해하지 말 것
- **줄바꿈** — 작업 트리는 CRLF(autocrlf=true). `sed -i` 와 통째로 다시 쓰는 도구는 파일을 LF 로 만든다.
  고친 뒤 `git diff --numstat` 의 추가(+) 줄 수로 확인할 것 — 줄끝이 틀어지면 파일 줄 수만큼 추가로 잡힌다
- **BOM 은 파일마다 다르다 — 있는 그대로 두어야 한다.** 대부분은 BOM 이 없지만
  `NoticeWindow.xaml` · `StudentExamWindow.xaml` 처럼 BOM 이 있는 파일도 있다(2026-10-30 확인).
  파이썬으로 고칠 때 `utf-8-sig` 로 **읽고 쓰면 없던 BOM 이 붙고**, 반대로 쓰기만 `utf-8` 로 하면 있던 BOM 이 사라진다.
  읽기·쓰기 모두 `utf-8` 을 쓰면 원래 상태가 그대로 보존된다. 고친 뒤 첫 3바이트를 바꾸기 전과 비교해 확인할 것.
  `Protocol.h` 에 BOM 이 붙으면 네이티브의 한글 해석이 달라진다
- **네이티브 소스 한글** — BOM 과 `/utf-8` 이 없어 C++ 안의 한글 문자열이 조용히 깨진다. 문자 코드값 배열로 적을 것
