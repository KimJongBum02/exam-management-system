# 파일명 · View/ViewModel/Service 책임 정리

처음 작성: 2026-09-16 (제안) · 최신화: 2026-09-28
기준 브랜치: `develop` (9/28 팀원 작업 병합 직후)
상태: **교수 프로그램은 적용 완료, 학생 프로그램은 아직 제안 단계**

이 문서는 **지금 코드의 파일 이름과 각 파일이 맡는 일**을 적는다.
교수 프로그램에 실제로 어떻게 적용했는지, 왜 그렇게 정했는지는 [01-리팩토링-적용-기록.md](01-리팩토링-적용-기록.md)에 있다.

## 원래 의도한 구조

```
View  ──바인딩──▶  ViewModel  ──호출──▶  Service  ──▶  네트워크 / 파일 / 프로세스
(화면)            (중간 다리)            (무거운 기능)
```

- **View**: 화면 배치만 맡는다.
- **ViewModel**: 자기 화면에 필요한 Service 를 불러 쓰고, 결과를 화면에 보여 줄 값으로 바꾼다.
- **Service**: 통신, 파일, 프로세스 제어 같은 실제 작업을 맡는다.
- **Store / State**: 여러 화면이 함께 보는 목록·상태(학생 목록, 경고 목록, 시험 단계 등)를 보관한다.
- **Model**: 값만 담는다.

## 4. 규칙

1. **끝말로 종류를 구분한다.** `…ViewModel`, `…Service`, `…Store`, `…State`, `…Native`. 화면은 `…Window`/`…Page`/`…Panel` 이지만 교수 쪽은 사용자가 정한 이름을 따른다(1-1).
2. **목록 한 줄짜리도 `…ViewModel`** 로 끝낸다. `Item` 접미사는 쓰지 않는다.
3. **퀴즈는 수업 확인 퀴즈 = `Quiz…`, 설문 = `Survey…`.** (교수 쪽 적용, 학생 쪽은 2-2)
4. **View 폴더에는 화면 파일만** 둔다. 뷰모델·모델·변환기는 각자 폴더로.
5. **파일 하나에 클래스 하나.** 예외: Model 폴더의 도메인 묶음 파일, 짝이 되는 열거형, 한 화면 안에서만 쓰는 작은 클래스.
6. **ViewModel 은 `NetworkService`, `File`/`Directory`, `Process` 를 직접 쓰지 않는다.** 반드시 Service 를 거친다.
7. **Service 는 창을 띄우지 않는다.** 결과값·열거형으로 돌려주고 창은 ViewModel·화면이 띄운다.

## 5. 작업할 때 주의할 점

### 이름 바꿀 때 (WPF)

- 파일명만 바꾸면 안 된다. `x:Class`, 클래스 이름과 생성자, 그 화면을 만드는 쪽(`new XxxWindow()`), `MainWindow.xaml.cs` 의 메뉴 전환을 함께 고친다.
- 바꾸려는 이름을 이미 다른 파일이 쓰고 있으면 두 파일을 한 번에 맞바꾼다(예: 설문 `QuizWindow` ↔ 퀴즈 `ClassQuizWindow`). 이때 git 에는 한쪽이 "내용이 통째로 바뀐 수정"으로 보인다.
- XAML 바인딩 경로(`{Binding Quiz.…}`)는 빌드에서 검사되지 않는다. 속성 이름을 바꾸면 XAML 을 직접 찾아 고친다.
- 폴더를 옮기면 이미지 경로가 깨진다. 예: `Icon="/Icon/Student.ico"`
- 팀원 브랜치와 충돌이 크게 나므로, 다른 작업이 병합된 직후에 한다.

### Service 로 옮길 때

- **자동 테스트가 없다.** 옮길 때마다 교수용과 학생용을 같이 켜서 접속 → 파일 배포 → 시험 시작 → 답안 수집 → 종료를 직접 확인한다.
- 기능 하나당 커밋 하나로 나눈다.
- `PacketReceived` 구독을 Service 로 옮길 때는 **구독 해제도 같이 옮긴다.** 빠뜨리면 이벤트가 두 번 처리된다.
