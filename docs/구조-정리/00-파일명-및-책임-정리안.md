# 파일명 · View/ViewModel/Service 책임 정리안

작성일: 2026-09-16
기준 브랜치: `develop` (9d9738f)
상태: **제안 단계 — 코드는 아직 바꾸지 않았다**

## 왜 정리하나

- 화면 파일과 ViewModel 이름이 서로 맞지 않아, 어떤 화면이 어떤 ViewModel을 쓰는지 파일 이름만 봐서는 알 수 없다.
- ViewModel이 통신·파일 처리까지 직접 맡고 있어서, 원래 의도한 구조(아래)에서 벗어났다.

### 원래 의도한 구조

```
View  ──바인딩──▶  ViewModel  ──호출──▶  Service  ──▶  네트워크 / 파일 / 프로세스
(화면)            (중간 다리)            (무거운 기능)
```

- **View**: 화면 배치만 맡는다.
- **ViewModel**: 자기 화면에 필요한 Service를 가져와 부르고, 결과를 화면에 보여 줄 값으로 바꾼다.
- **Service**: 통신, 파일, 프로세스 제어 같은 실제 작업을 맡는다.
- **Store**: 여러 화면이 함께 보는 상태(학생 목록, 경고 목록, 시험 단계 등)를 보관한다.

## 1. 현재 상태 진단

### 1-1. 교수 화면과 ViewModel 짝이 맞지 않는다

새 화면은 `View/Professor/*Page`로 만들었지만, ViewModel은 예전 화면(`View/_Legacy`) 기준 이름을 그대로 쓴다.
`_Legacy`는 빌드에서 빠져 있어서(`ProfessorUI.csproj`의 `Compile Remove`), `FileReadyViewModel`과 짝이던 `FileReadyView`는 지금 빌드에 없다.
ViewModel들은 [UiContext.cs](../../ExamManager/ProfessorUI/View/Professor/UiContext.cs)에 모아 두고 여러 화면이 나눠 쓴다.

| 메뉴 | 화면 파일 | 쓰는 ViewModel |
|---|---|---|
| 대시보드 | DashboardPage | Overview |
| 시험 준비 | ExamPrepPage | FileReady, FileDistribute, ExamStart, WhiteList, BlackList |
| 시험 관리 | ExamManagePage (+CheatAlertDetailPage) | FileDistribute, AnswerCollect |
| 알림·채팅 | ChatPage | Chat |
| 프로그램 관리 | **SecurityPolicyPage** | WhiteList, BlackList, Server |
| 종료 및 정산 | ExamEndPage (+EndSummaryPage) | AnswerCollect, ExamEnd |
| OX 퀴즈 | OXQuizPage | OXQuiz |
| 화면 모니터링 | ScreenMonitoringPage (+ScreenDetailWindow) | ScreenMonitoring |

그 밖의 문제:

- **메뉴 이름과 파일 이름이 다르다.** "프로그램 관리" 메뉴의 화면이 `SecurityPolicyPage`다.
- **View 폴더에 화면이 아닌 파일이 있다.** `ServerViewModel`, `ExamOverviewViewModel`, `UiContext`, `MenuEntry`, `ProgramListNameConverter`가 `View/Professor/`에 있다.
- **오타가 있다.** `NavigaitonStroe.cs`, 클래스명 `RightPanelViewMondel`, 폴더명 `_Legacy/AttenandceView`.

### 1-2. 학생 화면도 짝이 맞지 않는다

| 현재 | 문제 |
|---|---|
| `MainWindow` ↔ `LoginViewModel` | 로그인 창인데 이름이 MainWindow다 |
| `NotificationChatPanel` ↔ `SharedChatViewModel` | 이름이 서로 다르다 |
| `StudentLogin`, `StudentInputName`, `StudentInputNumber`, `InputIp` | 로그인 화면 부품인데 이름에 Login이 없다 |
| `StudentFile`, `StudentInformation`, `StudentTimer`, `StudentExamState` | 시험 화면 부품인데 이름에 Exam이 없다 |

### 1-3. ViewModel이 Service 일을 직접 하고 있다

**네트워크를 직접 다루는 ViewModel** (`NetworkService.Instance` 직접 호출)

| ViewModel | 직접 하는 일 |
|---|---|
| `ExamStartViewModel` | 시험 시작 신호 `Broadcast` 3회 |
| `FileDistributeViewModel` (415줄) | 파일 전송, 진행률·오류 이벤트 처리 |
| `ChatViewModel` | 채팅 전송, `PacketReceived` 구독 |
| `AnswerCollectViewModel`, `ExamEndViewModel` | 수집·종료 신호 전송 |
| 학생 `LoginViewModel` | `Connect`, `SendPacket`, `Disconnect` |
| 학생 `WaitingViewModel`, `SharedChatViewModel` | 연결 끊김 감지, 채팅 송수신 |
| 학생 `StudentExamViewModel` (486줄) | 연결 끊김과 패킷 수신을 직접 처리 |

반대 방향 문제도 있다. 교수 [App.xaml.cs](../../ExamManager/ProfessorUI/App.xaml.cs)는 받은 패킷을 `ScreenMonitoringViewModel.Instance`에 직접 넣는다.

**파일·프로세스를 직접 다루는 ViewModel**

- `OXQuizViewModel`: 퀴즈 목록을 JSON으로 직접 저장하고 불러온다.
- `FileReadyViewModel`: 폴더를 직접 탐색하고 폴더도 직접 만든다.
- `BlackListViewModel`, `WhiteListViewModel`: 실행 중인 프로그램 목록을 직접 가져온다(`Process.GetProcesses`).

**Service 폴더에 성격이 다른 파일이 섞여 있다** (교수용)

| 성격 | 파일 |
|---|---|
| 통신 | `NetworkService`, `ServerControl` |
| 상태 보관 | `StudentStore`, `AlertStore`, `ProgramControlStore`, `ExamState`, `FileDeployState`, `NavigaitonStroe` |
| 작업 | `ExamPackager`, `AnswerCollectService`, `QuizSessionService` |
| 목록 데이터 | `ProgramCatalog`, `ClassroomPrograms` |
| 사실상 ViewModel | `LayoutStore` (`ICommand` 보유, `_Legacy`에서만 사용) |

두 앱의 Service 이름도 맞지 않는다. 교수용에는 `NetworkService` 하나지만 학생용에는 `NetworkService`와 `NetworkControlService`가 따로 있다. `FileControlService`는 양쪽에 모두 있다.

### 1-4. 이미 잘 나뉜 부분

- 학생 보안 기능: `FirewallPolicyService`, `DnsRedirectService`, `ProcessControlService`, `ExamMonitorService`, `ScreenCaptureService`
- 교수 작업 기능: `ExamPackager`, `AnswerCollectService`, `QuizSessionService`
- `StudentItemViewModel`, `ScreenMonitoringViewModel`, `NoticeItem` 등은 데이터만 들고 있다.

**결론: 새로 설계할 필요는 없고, 섞여 들어간 코드를 Service로 옮기면 된다.**
Service 틀이 이미 있고, 꼬인 곳은 ViewModel 11개(교수 7, 학생 4)에 몰려 있으며, 꼬인 방식도 대부분 "ViewModel이 `NetworkService`를 직접 부른다" 한 가지다.

## 2. 규칙

1. **메뉴 하나에 폴더 하나.** 화면 파일과 그 화면 전용 ViewModel은 같은 폴더에 둔다.
2. **파일 이름은 `화면이름 + 역할`로 짓는다.** 한 화면에 ViewModel이 여러 개면 모두 화면 이름으로 시작한다.
   예: `ExamPrepPage`, `ExamPrepFileViewModel`, `ExamPrepStartViewModel`
3. **끝말로 종류를 구분한다.** `~Window`, `~Page`, `~Panel`, `~ViewModel`, `~Service`, `~Store`
4. **클래스 이름은 명사로 짓는다.** `ChangeScreen`처럼 동사형 이름은 메서드로 오해된다.
5. **여러 화면이 함께 쓰는 것만 `Shared/`에 둔다.**
6. **ViewModel은 `NetworkService`, `File`/`Directory`, `Process`를 직접 쓰지 않는다.** 반드시 Service를 거친다.

- `ProgramAllowList`/`ProgramBlockList`는 시험 준비 화면도 쓰지만, 목록을 편집하는 곳이 프로그램 관리 화면이라서 `ProgramPolicy/`에 둔다.
- **ShellWindow → MainWindow로 바꾸는 이유:** 이 창은 앱을 켜면 뜨는 메인 창("시험 운영")이다. 왼쪽 메뉴, 상단바, 가운데 페이지 영역으로 되어 있고, 메뉴 전환, 시험 단계별 메뉴 잠금, 작업표시줄 깜빡임을 맡는다. "Shell"은 팀원에게 낯선 용어라서 바꾼다. 단, `_Legacy/MainWindow`와 이름이 겹치므로 `_Legacy`를 먼저 지워야 한다.
- **MenuEntry → MainMenuItem으로 바꾸는 이유:** 메인 창 왼쪽 메뉴의 한 줄(`Name`, `Enabled`, `LockReason`, `SetGate`)을 담는 작은 ViewModel이라서, 메인 창 소속임이 드러나게 한다.
- 영어 화면 이름(`ExamPrep`, `ProgramPolicy`, `NoticeChat` 등)은 팀 합의로 바꿔도 된다. 규칙만 지키면 된다.

## 4. 책임 이동안 (ViewModel → Service)

### 목표 모습 (예: 시험 시작)

```
지금:  ExamPrepPage → ExamStartViewModel ──(Broadcast × 3)──▶ NetworkService

목표:  ExamPrepPage → ExamPrepStartViewModel → ExamControlService.StartExam()
                                                      └─▶ NetworkService
```

ViewModel에는 "버튼이 눌리면 `StartExam()`을 부르고, 결과를 화면용 값으로 바꾼다"는 코드만 남긴다.

### ViewModel별 이동 대상

| ViewModel | 옮길 기능 | 받을 Service |
|---|---|---|
| ExamStart, ExamEnd, AnswerCollect | 시작 · 종료 · 수집 신호 | `ExamControlService` (신규) |
| FileDistribute | 파일 전송, 진행률 | `FileDeployService` (`FileDeployState` 확장) |
| FileReady | 폴더 탐색, 압축 | `ExamPackager` 확장 |
| Chat | 채팅 송수신 | `ChatService` (신규) |
| OXQuiz | JSON 저장 · 불러오기 | `QuizSessionService` |
| BlackList, WhiteList | 실행 중 프로그램 조회 | `ProgramCatalog` |
| 학생 Login, Waiting | 접속, 로그인 패킷 | `NetworkControlService` 정리 |
| 학생 StudentExam, SharedChat | 패킷 수신 처리, 채팅 | `ExamSessionStore`, `ChatService` |

`MessageBox.Show`, `OpenFileDialog`를 ViewModel에서 쓰는 곳도 많지만, 작은 WPF 프로젝트에서는 흔한 방식이라 이번 범위에서는 제외한다.

## 6. 작업할 때 주의할 점

### 이름 바꿀 때 (WPF)

- 파일명만 바꾸면 안 된다. `x:Class`, 네임스페이스, `xmlns:local`을 함께 고친다.
- 폴더를 옮기면 이미지 경로가 깨진다. 예: `Icon="/View/LoginView/Assets/yuhan.png"`
- 클래스명은 Visual Studio에서 **F2(이름 바꾸기)**로 바꾸고, 파일은 **`git mv`**로 옮겨 변경 이력을 남긴다.
- 화면 하나당 커밋 하나로 나누고, 커밋마다 빌드를 확인한다.
- 팀원 브랜치와 충돌이 크게 나므로, 다른 작업이 머지된 직후에 진행한다.

### Service로 옮길 때

- **자동 테스트가 없다.** 옮길 때마다 교수용과 학생용을 같이 켜서 아래 흐름을 직접 확인한다.
  접속 → 파일 배포 → 시험 시작 → 답안 수집 → 종료
- 기능 하나당 커밋 하나로 나눠서, 문제가 생기면 어디서 깨졌는지 바로 찾을 수 있게 한다.
- `PacketReceived` 구독을 Service로 옮길 때는 **구독 해제도 같이 옮긴다.** 빠뜨리면 이벤트가 두 번 처리된다.

### 다시 꼬이지 않게

AI로 작업하면서 구조가 꼬인 것으로 보인다. 지금 `CLAUDE.md`/`AGENTS.md`에는 일반적인 작업 원칙만 있고 이 프로젝트의 구조 규칙은 없다.
2장의 규칙을 두 파일에 추가해서, AI가 작업할 때마다 읽도록 한다.
